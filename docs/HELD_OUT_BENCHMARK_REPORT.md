# AgentOpt — Held-Out Multi-Repository Benchmark & Empirical Validation Report (`v0.1.0`)

> **Executive Summary:**  
> To evaluate the modular `v0.1.0` architecture (`FAST`, `BALANCED`, `STRICT`) without overfitting to the 30-task development set, we constructed a **frozen 15-task multi-repository held-out benchmark** spanning **5 distinct software repositories** (`repo-fintech-ledger`, `repo-http-gateway`, `repo-workflow-dag`, `repo-schema-sanitizer`, and `repo-search-analytics`) and executed **60 real LLM tool-calling trajectories** (`15 tasks × 4 modes`) plus **8 development-set regression verification runs** using `qwen2.5:7b` via Ollama (`/api/chat`, `temperature: 0`).  
> - **Independent Held-Out Completion Rate (`N = 15` unseen tasks):** **`80.0%` (`12/15`)** across `FAST`, `BALANCED`, and `STRICT` vs. **`46.7%` (`7/15`)** for `baseline` (**`+33.3%` absolute gain**, **`5` paired task wins, `0` paired task losses, `10` ties**).  
> - **Provider-Reported Token Efficiency (`FAST` mode):** **`-42.1%` mean input tokens** (`2,994 → 1,734`, 95% paired CI `[-64.2%, -20.0%]`, median `3,508 → 1,478`), **`-43.7%` mean output tokens** (`355 → 200`), **`-42.3%` mean total inference tokens** (`3,349 → 1,934`), and **`-41.1%` wall-clock latency** (`8,259ms → 4,867ms`).  
> - **Prespecified Default Mode Selection:** Under our prespecified decision rule (*"Default to BALANCED only if it proves superior to FAST under a prespecified, reproducible evaluation. Otherwise default to FAST"*), `BALANCED` achieved the exact same **`80.0%` (`12/15`)** held-out accuracy as `FAST` while consuming more input tokens (`2,402` vs. `1,734`) and latency (`6,342ms` vs. `4,867ms`) due to bounded verification retries on the 3 tasks that exceeded `qwen2.5:7b`'s reasoning capacity. Therefore, **`FAST` is selected as the default mode** in `DEFAULT_CONFIG`.

## 1. Methodology & Explicit Epistemic Distinctions

To maintain scientific rigor and prevent conflating distinct forms of evidence, this report strictly separates four dimensions:

### 1.1 Development Set vs. Frozen Held-Out Test Set
1. **Preliminary Development Set (`30` tasks, `1` repository — [`src/real-benchmark/tasks.ts`](../src/real-benchmark/tasks.ts)):**
   - Used in our initial audit (`benchmarks/real-llm-results.json`, `60` runs) to identify failure modes in `v0.1.0`, diagnose the two regressions (`task_01_lru_eviction` and `task_03_deep_freeze_array`), and tune AST symbol extraction and distractor filtering.
   - Reported strictly as **preliminary / development evidence** in Section 5 below.
2. **Frozen Multi-Repository Held-Out Test Set (`15` unseen tasks, `5` repositories — [`src/real-benchmark/held-out-tasks.ts`](../src/real-benchmark/held-out-tasks.ts)):**
   - Frozen *after* all code changes to `src/context/index.ts` and `src/core/optimizer.ts` were finalized. No prompt, scoring weight, or heuristic was tuned on these 5 repositories or 15 tasks.
   - Each repository contains realistic multi-module ES6 source trees, cross-file imports, class methods, and distractor utility modules (`src/core/env.mjs`, `src/utils/logger.mjs`, `src/utils/clock.mjs`, `src/utils/id.mjs`).

### 1.2 Input Tokens vs. Output Tokens vs. Total Inference Tokens
All token counts in [`benchmarks/held-out-modes-results.json`](../benchmarks/held-out-modes-results.json) are **exact provider-reported values** summed across every `/api/chat` turn in a task trajectory:
- **Input Tokens (`prompt_eval_count`):** Prompt and context tokens processed by the model across all turns in the trajectory.
- **Output Tokens (`eval_count`):** Completion and tool-call tokens generated by the model across all turns.
- **Total Inference Tokens (`prompt_eval_count + eval_count`):** Combined prefill + decode token volume.

### 1.3 Observed Local Resource Usage vs. Estimated Monetary API Cost
- **Observed Resource Usage:** Local wall-clock execution time (`wallClockMs`), hook execution overhead (`hookOverheadMs`), LLM API turn count (`llmTurns`), and tool calls (`toolCalls`) measured directly on Apple Silicon (`darwin arm64`). Actual monetary expenditure for local Ollama execution is **`$0.00`**.
- **Estimated Monetary Cost (`estimatedApiCostUsd`):** Projected equivalent cloud API cost at standard frontier pricing (`$3.00 / 1M` input tokens, `$15.00 / 1M` output tokens) to allow direct comparison of token-level unit economics.

### 1.4 Real Local Tool-Calling Model Runs vs. Live Vendor Coding-Agent Runs
- **Local Tool-Calling Model Harness ([`src/real-benchmark/evaluate-modes.ts`](../src/real-benchmark/evaluate-modes.ts)):** Runs a real local LLM (`qwen2.5:7b`) with live tool definitions (`read_file`, `write_file`, `edit_file`, `run_command`, `list_files`) and real `node --test` execution in isolated temporary workspaces. This validates AgentOpt's core engines (`ContextEngine`, `TaskVerificationEngine`, `FailureDetectionEngine`, `ProjectMemoryStore`), **not** proprietary third-party CLI binaries.
- **Live Vendor Coding-Agent Validation (Section 4):** Google Antigravity 2.0 was validated separately using live Google Antigravity subagents (`dc463b89`, `f940631b`, and `d9ab09d1`) executing real `.agents/plugins/agent-opt/hooks.json` lifecycle hooks. Claude Code, Cursor, and OpenAI Codex adapters are schema-tested in CI (`npm test`) and labeled **Experimental / Schema-Validated**.

### 1.5 Task-Level Uncertainty vs. Run-Level Variability
- **Task-Level Uncertainty:** Reported using **95% Wilson score confidence intervals** over the $N=15$ independent held-out tasks (and $N=30$ development tasks), plus paired $t$-distribution 95% confidence intervals on per-task token deltas ($\Delta_i = \text{Tokens}_{\text{mode}, i} - \text{Tokens}_{\text{baseline}, i}$).
- **Run-Level Variability:** With `temperature: 0` on local `qwen2.5:7b`, run-to-run variance on identical prompts is near-zero for token counts and deterministic for workspace edits, whereas wall-clock latency exhibits $\pm 4\%$ OS scheduling variability.

### 2.4 Analysis of the 3 Preserved Held-Out Failures (`ho_03`, `ho_05`, `ho_11`)

In all 3 failed held-out tasks, `baseline` also failed (`0` regressions introduced by `FAST`, `BALANCED`, or `STRICT`):
1. **`ho_03_fx_cross_conversion` (`repo-fintech-ledger`):** Requires editing two files (`src/fx/rates.mjs` to add `CHF: 0.9` and `src/fx/converter.mjs` to round `convertCurrency` to 2 decimals). `qwen2.5:7b` edited both files in `FAST` mode (`write_file(src/fx/rates.mjs) -> write_file(src/fx/converter.mjs)`), saving `-23.8%` input tokens (`3,508 → 2,674`), but wrote an inverted cross-rate formula `(amount * fromRate) / toRate` instead of `(amount / fromRate) * toRate`. In `BALANCED` mode, the silent `Stop` probe caught the failing test (`StopBlocked(FAILED)`) and prevented unverified completion. Notably, when we ran the exact same task on **Google Antigravity 2.0** (Section 4), the stronger model wrote the exact formula and passed 100%.
2. **`ho_05_route_param_matcher` (`repo-http-gateway`):** `baseline` hallucinated a non-existent file (`write_file(src/utils/pathExtractor.mjs)`). With AgentOpt (`FAST`, `BALANCED`, `STRICT`), `qwen2.5:7b` edited the exact target file (`src/router/matcher.mjs`), but its loop did not return `null` when static path segments differed (`patParts[i] !== pathParts[i]`). `BALANCED` mode's silent probe caught the failure and marked the session `FAILED`.
3. **`ho_11_mask_credit_card` (`repo-schema-sanitizer`):** `qwen2.5:7b` used `.slice(-4).padStart(str.length, '*')`, which also masked hyphen separators instead of preserving non-digit separators or stripping them as expected by the oracle. `BALANCED` mode's silent probe accurately flagged the session as `FAILED`.
